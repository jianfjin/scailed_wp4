System Architecture

Three-layer monolith. Multi-container Docker Compose (5 services). Deployed via docker compose up -d. PostgreSQL runs in its own stateful container with a named volume — never co-located with the application.

Architecture Decision: Multi-container monolith, not microservices. 9/9 council seats agree. User base is < 500 invited stakeholders. Docker Compose with 5 services: traefik (proxy) · frontend (nginx + Vue 3) · backend (FastAPI, horizontally scalable) · postgres (PG16 + Apache AGE, stateful with named volume) · redis (optional cache). No K8s, no service mesh, no event bus. See deploy/docker-compose.yml.
Module Structure (project root):
api/ (FastAPI routes) · core/ (assessment, solver engines) · adapters/ (WP2/3/5/6/7/8) · models/ (Pydantic + SQLAlchemy) · rules/ (*.yaml) · migrations/ (Alembic) · config/ (env-specific settings) · exceptions/ (custom error hierarchy) · services/ (business logic layer) · scripts/ (CLI admin tools) · tests/ + tests/fixtures/

Architecture Decision: PostgreSQL runs in its own independent container with a named volume (scailed_pgdata). It is never co-located with the application container. This is Docker best practice — one process per container. The database is only accessible on the backend internal network; it has no exposure to the frontend network or the public internet. Backend scales horizontally: docker compose up -d --scale backend=3.

Frontend: Dual-Option Strategy

Council debate 2026-05-15 initially preferred Vue 3. However, a subsequent market-data investigation (GitHub stars, npm downloads, EU job market analysis) revealed React's 10× dominance in Europe. Revised position (2026-05-15): frontend framework selection deferred to CHARITE/Epidata input. DataWego prepared to deliver in either React or Vue 3.

CandidateStatusMarket PositionDecision Factor
React 19 + TypeScript ✅ PRIMARY GitHub 245K ★ · npm 132M/week · Next.js 36M/week. React dominates EU/German job market by 5-8×. CHARITE (Berlin) would have abundant local developer supply. Recommended if CHARITE plans to maintain in-house or hire EU contractors.
Vue 3 + TypeScript ✅ VIABLE GitHub 54K ★ · npm 12M/week. Strong in China/Asia. Gentler learning curve for non-frontend developers due to HTML-like template syntax. Recommended if CHARITE has existing Vue codebase or non-frontend staff maintaining.
Svelte 5 ✕ REJECTED Niche ecosystem. Opaque compiled output. CHARITE can't Google problems. No hiring pool in Berlin. —
SolidJS ✕ REJECTED Alien signal-based paradigm. Tiny community. Double learning risk (framework + TypeScript). —
Strategic Decision: We will NOT finalize the frontend framework unilaterally. The email to Epidata (v3) explicitly asks: (1) Who maintains the frontend during T4.2/T4.3 — CHARITE internal IT, external contractor, or re-tender? (2) Does CHARITE have an existing frontend technology preference or constraint? (3) Can we connect with CHARITE's IT contact for technical alignment? DataWego's development cost is effectively identical for either framework (~500 lines of frontend code). We will lock the choice after receiving CHARITE's feedback, before M1 prototype delivery.
Market Data (May 2026): React npm downloads (132M/week) exceed Vue (12M/week) by 10.7×. Next.js alone (36M/week) outpaces the entire Vue ecosystem (Vue + Nuxt = 14M/week) by 2.6×. In the EU/German market, React job postings outnumber Vue 5-8:1. However, Vue remains a strong choice for teams with limited frontend specialization — its template syntax is instantly readable by anyone who knows HTML. The right answer depends on CHARITE's actual maintenance plan, which we do not yet know.

Database: Alternatives Evaluated

Council debate 2026-05-15: 5 seats (Musk/Linus/Dijkstra/Guido/Xiaolong) evaluated PostgreSQL vs DuckDB vs SQLite. Verdict: PostgreSQL 16 + Apache AGE unanimously reaffirmed. DuckDB/SQLite rejected as categorically unsuitable.

CandidateVerdictFatal Flaw
PostgreSQL 16 + AGE ✅ KEEP None. Satisfies all 4 irreducible requirements: concurrent OLTP, ACID audit trail, Cypher graph queries, operational maturity.
DuckDB ✕ REJECTED OLAP engine, not OLTP. No concurrent writes (database-level lock). No graph extension (no Cypher, no DAG traversal). No ACID for audit trail. "It's DuckDB, not DuckTP." — Xiaolong
DuckDB + PG hybrid ✕ REJECTED Two connection pools, two backup strategies, two failure modes. Violates Musk's Algorithm Step 2: "delete any part or process you can." No analytics workload justifies the operational surface area.
SQLite + Litestream ✕ REJECTED Single-writer bottleneck. No graph extension — would externalize to NetworkX (already rejected at 200+ nodes). Litestream async S3 replication loses audit log seconds on crash → EU AI Act non-compliance.
Neo4j Community ✕ REJECTED Already rejected by May 13 council resolution. "No Neo4j" is council law.
Dijkstra's formal objection to DuckDB: "DuckDB has no graph extension, no Cypher, no recursive traversals. You would externalize the graph to NetworkX — which you already rejected at 200+ nodes. At 10⁴ nodes, this is algorithmic suicide. The audit log becomes a probabilistic audit log. Simplicity is a prerequisite for reliability — a hybrid architecture doubles your moving parts and halves your correctness confidence."
Xiaolong's PG tuning guide (for 8 GB RAM): PG can run comfortably on 2 GB RAM with proper config: shared_buffers=256MB, max_connections=30, work_mem=8MB, effective_cache_size=4GB. Use PgBouncer for connection pooling. PG's "heaviness" is a configuration problem, not an architecture problem. "Time should be spent tuning, not selecting."

Agent-D Comparison & Fusion Verdict

2026-05-15: 8-seat council debate (Musk/Linus/Dijkstra/Guido/Xiaolong/Xuefeng/Jobs/Jensen) compared Parliament's design against an independent Agent-D proposal (docs/, 11 documents). 8/8 unanimous fusion verdict.

DimensionParliamentAgent-DVerdict
Graph Engine PG + Apache AGE Neo4j Parliament — AGE sufficient for 10⁴-node DAG. Dijkstra: "O(V+E) complexity class unchanged." Neo4j ops burden (€31.5K, second DB) unjustified. V2 sunset clause: if GraphRAG/ontology reasoning scope confirmed, re-evaluate.
Deployment Docker Compose K8s + Helm + Terraform + Azure Parliament — K8s control plane eats 1.15GB RAM on 8GB VM. 85% of German hospitals don't run K8s. Docker Compose + Makefile is enterprise-grade for 500 users.
D4.1 Scope 3 modules (CSP engine + questionnaire + dashboard/PDF) 6 modules (+AI Copilot, GraphRAG, regulatory intelligence, use-case validation) Parliament — Agent-D scope costs €260K-320K (Xuefeng audit), exceeding €145K by 80-120%. AI Copilot rejected: EU AI Act liability + €42K cost.
Repo Strategy Single repo 4-5 repos Parliament — Premature decomposition for solo developer. Cross-cutting changes need 1 commit, not 4 PRs.
AI Layer Deterministic rule engine only RAG + LLM Copilot + GraphRAG Parliament — Jobs: "Not a feature. A lawsuit wearing a chat interface." Deterministic = auditable = EU AI Act safe harbor.
Start Strategy Wait for WP3/WP8 M3 schema Build immediately with mock data Agent-D — Parliament's biggest blind spot corrected. Xuefeng: "Waiting 3 months costs €42K opportunity. Rebuilding from wrong assumptions costs €10-14K." M0 start with HL7 FHIR standards.
Data Contracts Brief JSON/CSV mention Detailed per-partner JSON schemas Agent-D — Adopt docs/07 specs as contract appendix. Guido: "Exactly what consortiums need." But only at WP boundaries, not internal microservice plumbing.
Fusion Architecture (8/8 unanimous): One repo. PG16 + Apache AGE (one database). React frontend. Docker Compose (5 containers, single VM). Three D4.1 modules: CSP pathfinding engine + questionnaire wizard + basic dashboard/PDF. M0 start with mock data. WP-boundary JSON schemas in contract. Deterministic rule engine. No Neo4j, no K8s, no AI Copilot, no GraphRAG.

Agent-D's strongest contributions (absorbed): mock-data-first strategy, detailed data contracts, product UX vision, ontology as first-class artifact.
Agent-D's over-engineering (rejected): Neo4j, K8s+Helm+Terraform, AI Copilot, 6-module scope, 4-5 repo split.
Cost reality: Agent-D blueprint = €260K-320K. Parliament fusion = €87.5K. Remaining €57.5K buffer for uncertainty.

Architecture Risks & Tradeoffs

CRITICAL WP3 roadmap format is single point of failure

If CHARITE delivers a PDF instead of structured JSON, the graph engine cannot function. Mitigation: demand JSON/CSV node-edge list with topological proof by M2. No schema = no code. WP3 Plan B: data extraction layer — if structured data is delayed, implement a lightweight extraction pipeline that parses WP3 deliverables into the canonical node-edge format with manual QA sign-off.

HIGH WP8 legal constraints may not be formalizable

Lawyers write "should" and "may" — SAT solvers need boolean predicates. Architecture handles this with soft checks: flag risks rather than hard-block. Rules hot-loadable when WP8 updates.

MEDIUM CHARITE must maintain code in T4.3

Write "boring code" — no clever abstractions, no custom DSL, no deep inheritance. README explains deployment, not design philosophy. They need to add a rule, not understand the engine.

LOW Performance at scale

< 500 users, < 10⁴ roadmap nodes. Constrained graph search on DAG is sub-millisecond. Premature optimization is Mathematics Inc.'s enemy.
