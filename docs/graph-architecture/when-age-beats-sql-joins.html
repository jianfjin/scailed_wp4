SCAILED WP4 — When Does AGE Beat SQL JOINs?

Document version: 2026-05-19  |  Branch: feature/mock-upstream-rest-services  |  Context: Follow-up to the PostgreSQL + AGE graph architecture doc — answering why have AGE at all if SQL can do the job.

At V1 scale (< 100 nodes), AGE has zero advantage.
Python BFS + SQL JOINs are faster, simpler, and have no network overhead.
AGE is a strategic reserve — sleeping investment, not active weapon.

1. Current vs. AGE: Head-to-Head

What You Do Now

Shortest path: Python BFS, O(V+E), dict lookup O(1)

Network: Zero (in-process)

Code: 30 lines of readable Python

Winner at this scale

If You Used AGE Cypher

Shortest path: MATCH p = shortestPath(...) — parser → planner → executor

Network: asyncpg round-trip

Code: 3 lines of Cypher

AGE only wins on expressiveness, not performance

Honest assessment: AGE is currently an expensive ornament. Compile cost, dual-write maintenance, advisory lock overhead — all paid, but the query layer doesn't use any of it.

2. When AGE Starts Making Sense

The threshold is not node count. It's query complexity.

2.1 Variable-Length Paths with Edge Constraints

"Find a path from A to B, skip nodes with maturity_level < 3, and ensure at least one node in the 'compliance' dimension."

SQL Recursive CTE

WITH RECURSIVE path AS (
  SELECT node_id, ARRAY[node_id] as visited, 0 as depth
  FROM roadmap_nodes WHERE node_id = 'A'
  UNION ALL
  SELECT r.node_id, p.visited || r.node_id, p.depth + 1
  FROM path p
  JOIN roadmap_nodes r ON r.node_id = ANY(...)
  WHERE NOT r.node_id = ANY(p.visited)
    AND r.maturity_level >= 3
    AND p.depth < 6
)

Possible, but readability collapses as constraints grow.

AGE Cypher

MATCH p = (a {node_id:'A'})-[*1..6]-(b {node_id:'B'})
WHERE ALL(n IN nodes(p) WHERE n.maturity_level >= 3)
  AND ANY(n IN nodes(p) WHERE n.dimension = 'compliance')
RETURN p

Declarative. Reads like English.

2.2 Graph Analytics

OperationSQLCypher / AGE
Betweenness centrality Not feasible Built-in or one-line extension
Community detection (Louvain) Not feasible Extensible in AGE
"All downstream nodes of X" WITH RECURSIVE (n)-[*]->(m)
Cycle detection (DAG validation) Painful workaround EXISTS((n)-[*]->(n))

None of these are needed in V1. In V2, "how many stakeholders does this compliance path impact?" — SQL can't answer that.

2.3 Pattern Matching

"Find all subgraphs matching: stakeholder → compliance_node → blocked by missing_capability"

Cypher is a native graph pattern matching language. SQL requires nested multi-level JOINs with subqueries. As pattern complexity grows, the SQL version becomes write-only.

This is technical debt with a purpose, not an architectural defect.

4. The Defense

"Better to have AGE running in the container now — schema aligned, data synced, tests passing — than to stop everything and install it when V2 suddenly needs graph analytics."

The cypher_query() passthrough interface already exists. The Cypher query templates are written and tested. The switchover cost is one line of code.

V2 will demand:

  • "Show me the impact radius of changing this regulation"
  • "Which stakeholder paths are blocked by missing capability X?"
  • "Community-detect the roadmap and find isolated requirements"

AGE will be ready. Until then, it's a sleeping investment.

5. Summary
