# Pathfinder 跨 WP 语义治理基线

日期：2026-11-26。状态：本仓库设计讨论基线已确认，第 13 问整体确认完成，本轮访谈结束。

## 目的与范围

本轮优先解决跨 WP 的术语、内容所有权和变更责任，范围为 WP2/WP3/WP4/WP8 的 Pathfinder 交界。采用 DDD 的共同语言、责任边界和业务不变量来组织讨论；当前[模块化单体与确定性核心](../13_merged_pathfinder_design.md)是现有架构背景，核心代码重构、全项目统一 DDD 规范和供应商验收范围未在本轮决定。

现有证据支持项目已采用部分 DDD 做法；本轮文档使若干领域含义和责任更加明确，不能因此宣称现有实现已完整满足所有决定。工作包、业务内容域与软件限界上下文需要区分。

## 语义协作与内容责任

[上下文索引与协作图](../../CONTEXT-MAP.md)保留采购文件与跨 WP 业务语言两个语境，避免把采购文件的项目中性称谓当作运行域的全部词汇。

| 内容域 | 责任边界 |
| --- | --- |
| WP2 分类参考知识 | 确认参与者类型、分类词汇等源内容的业务含义 |
| WP3 路线图知识 | 确认路线图节点、关系和前置条件的业务含义 |
| WP8 规则知识 | 确认项目规则及引用的业务含义 |
| WP4 评估与导航 | 负责保持源含义的适配、协调和评估执行 |

WP4 不以集成协调职责替代来源 WP 的业务确认。问卷起草、评审与正式签署的具体分工仍需结合现有边界方案落实。

## 已确认的共同语言与业务约束

| 主题 | 共识 | 记录 |
| --- | --- | --- |
| 主体与角色 | 机构、参与者类型、场景角色分别表达，同一机构可在不同场景承担不同角色 | 词表；第 4 问 |
| V1 身份范围 | 独立评估会话，不建立机构档案或跨会话机构历史 | ADR 0005；第 5 问 |
| 类型参考能力 | 不自动继承为本次评估能力 | ADR 0006；第 6 问 |
| 未知与否定 | 无回答且无其他依据时保持未知，不转为肯定或明确否定 | ADR 0006；第 7 问 |
| 条件性方向 | 必要能力未知时可提供方向和待补信息，明确尚不能确认路径可执行 | ADR 0006；第 8 问 |
| 自报与核验 | 自报可用于注明依据的推演，保留自报、未核验性质；填写完整度不等于真实性核验 | ADR 0006；第 9 问 |
| 普通内容交付 | 内容方确认，WP4 按既定约定验收，无须每批重复双边人工签署业务内容 | ADR 0004；第 10 问 |
| 交界变更 | 改变交界语义或兼容约定时由受影响供需双方批准 RFC，结构未变也可能发生语义变更 | ADR 0004；第 3、10 问 |
| 内容撤回 | 撤回版本停止用于生成新建议，历史结果保留并呈现来源已撤回 | ADR 0007；第 11 问 |
| 撤回影响范围 | 暂停依赖被撤回精确版本的新推演，其他已确认有效且无该依赖的组合继续使用 | ADR 0007；第 12 问 |

完整定义见[交界语言词表](./pathfinder-boundaries/CONTEXT.md)。具体选择与证据见[讨论记录](./2026-11-26-cross-wp-ddd.md)。

## 已有实现基础与差异

既有版本化快照、完整依赖校验、先准备后原子激活及评估版本绑定为后续落实提供基础。它们保证部分结构和一致性条件，内容含义的确认及撤回后的业务有效性还需要领域约定。

| 已观察到的实现或约定 | 与本轮共识的关系 | 后续设计需处理的事项 |
| --- | --- | --- |
| [旧有能力推导](../../pathfinder/services/derived_readiness.py)从 WP2 记录生成能力、缺口及成熟度 | 与类型参考不自动成为本次事实的边界需对照 | 明确旧推导路径的适用范围、输出来源与字段含义 |
| [规则条件求值](../../pathfinder/core/compliance.py)仅返回真假，否定直接反转 | 尚未表达独立的未知结果 | 确认比较、否定、复合条件与未知的语义及兼容策略 |
| [问卷能力构建](../../pathfinder/core/questionnaire.py)直接收集能力集合，confidence 依据填写情况形成 | 来源与核验不能由一个数字代替 | 表达自报来源、核验状态及未知，并保留必要依据 |
| [基础推荐组装](../../pathfinder/core/recommend.py)使用 ready/blocked 等表达，其他层处理部分 unverified/degraded | 尚不能等同于已具备条件性方向和待补信息的完整模型 | 确认结果字段、状态命名和含义，避免仅重命名状态 |
| [交界契约](../../contracts/envelope.schema.json)及当前激活流程缺少完整撤回通知与响应约定 | 新批次失败保留旧输入，不等于被撤回旧输入仍可用 | 明确撤回来源、版本范围、依赖影响、历史标识和恢复条件 |
| 现有治理描述内容所有者、双边 RFC 与管理员接入 | 业务确认与接入授权是不同职责 | 落实确认记录、审批依据、实际负责人及各 WP 的正式认可 |

这些是后续设计与实现评审的输入，尚未转成代码修改或共享契约版本变更。

## 待工程细化及跨 WP 落实的事项

- 四类内容模型的进一步边界、问卷内容的评审责任，以及核验主体与核验依据。
- 撤回通知的可信来源、明确标识、传播验证与恢复条件；受影响暂停使用不替代下游内容方的撤回决定。
- 普通内容变更与交界语义变更的实际分类依据、记录和兼容示例。
- 未知、自报、核验、条件性方向与现有结果字段的兼容表达。

涉及交界约定的调整按已确认的双边 RFC 原则处理，技术实现选择在相应设计中再决定。本仓库讨论中的接受状态不等同于已经取得所有 WP 的正式签署。
